# /new-project

Read the applied version and project ledger. Treat the argument as a description. When omitted ask for a short description, allowing the person to leave the idea for later. Use any already supplied project-one facts. Suggest a slug. Apply the sealed topology: sibling ../SLUG, nested projects/SLUG, configured custom parent, or ask each time. Ask only for per-project fields designated by the policy. Verify ancestor instructions and Git roots. Resolve the absolute path on the actual OS. Create a missing configured parent directory before invoking the helper. Check for overlapping registered project roots, existing host instructions, skills and files before installing. Preserve unrelated work and remotes. If two files require integration, agree on a merge or a separate directory and restart preflight.

When there is real project context, prepare an interpretation in the current Kandoo dossier, in the project document language. Preserve provenance and distinguish assumptions from user words. Otherwise leave it empty. For a shared method update the non-secret instructions in kandoo_docs/living/context/server.md; reuse the configured scope, and include only the shared target's authorized credentials from ignored kandoo_docs/secrets/credentials.md. Verify protected local access/ACLs. Missing credentials stay pending. Allocate nothing in the method workspace.

The assistant invokes `python3 scaffold.py create SLUG DESTINATION` with separate, OS-quoted arguments. Add `--interpretation FILE` only for the prepared interpretation, and `--shared-access` when the authorized shared access is available. The helper verifies the applied snapshot, installs full project-only command bodies and pointers, initializes a project-root repository or uses the configured existing Git owner, and registers the path and revision. Inspect collisions before retry. A registered result is resumed in place. After interruption inspect both ledger and destination; recover only files verified against the sealed version. The locks in kandoo_docs/living/.scaffold.lock and the destination .scaffold.lock record a PID. After a hard interruption, verify that its process has ended and reconcile the destination against the seal before clearing that abandoned lock. Never clear a nonempty destination.

Verify the job-specific intake guide, interpretation, constitution, all host copies, status and git root. Localize the project server record if present. Preserve its technical identifiers. Verify the local credentials file is ignored and protected if present. The helper preserves existing .gitignore content and appends the project rules as needed. Review the resulting diff. Apply the configured remote policy. For automatic creation use the confirmed provider, namespace and visibility, verify the new remote before its first push and record the result. Preserve a working remote, record the credential-free URL and backup state in the project ledger; local-only is valid. Verify a safe initial checkpoint when identity is available, staging only reviewed project files. Record actual checks and hand off with the absolute folder for the new AI session, its docs/ Obsidian vault, the editable docs/versions/0.1/00-user-idea-input.md guide, existing/ for material to adopt, samples/ for reference outputs, docs/versions/0.1/sources/ for notes, and /idea (or $idea). Keep Kandoo progress independent.

Creation copies the current Kandoo conversation and document languages to the project profile. Verify both before the first project message, including for offline projects and non-English intake. Use --shared-access for the authorized common API key when the sealed policy is shared, including when Server mode is none.
