# Method workspace

The product of this workspace is one evolving project template. Read the profile, status, mission, workflow and current dossier. Apply the review protocol in this folder. Participants work in Markdown in this vault. The assistant operates files, Git and native tools. Preserve participant work, authorization and source records. Limit any sample import to material the participant supplies. Keep secrets in ignored Markdown with restrictive access. Never include secrets, personal examples or real project history in reusable payloads.

Keep one writer for method changes. Read current status before mutation, record the active version, stage, pending review, evidence and next action, and append a dated event after each meaningful change. Resume a partial install using its recorded starter and version. Keep registry, core commands and locally owned Git history throughout. A configured bootstrap invocation shows saved status and routes method edits through /new-version. Core procedures may be repaired directly when needed. Named commands and ordinary requests follow the same rules. Ask for a missing required argument.

On every reply show the method's ordered setup steps in the conversation language with ✅ completed, 🔵 current, ⬜ remaining and ⏭️ skipped. At selection show both /pick-job and /create-job branches. Mark the unused branch skipped once chosen. Display pending review and end with one exact next action. After setup show applied Kandoo version, projects, revision lag and notes waiting. Count unprocessed Markdown notes in registered projects’ docs/method-notes/ (exclude README), using the receipt in living/note-receipts.md keyed by project slug, filename and content hash. Use filenames and hashes to count; read note contents during inspection/version review. If a path is unavailable show the known count and identify the unknown project. Never silently count it as zero. Project progress belongs in the work window.

The Kandoo version starts at 0.1. Moom's release number identifies the harness. Each project has a separate version sequence. Applying a new method affects future projects. Adopting it in an existing project requires /migrate. Do not alter a registered project during /inspect or /apply. No automatic upstream sync. Notes for the instructor are write-only and manually handed over.
