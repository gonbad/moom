# Review and version input

Before changing a result, read its primary input and subsequent numbered analysis,
answers and COMMENT/نظر feedback in order. Later decisions override earlier ones.
Extract the requested problem, audience actions, sequence, language, required inputs
and removed content. Inherited specifications are context; they cannot override the
new source. Compare the result to that contract separately from rendering or tests.

First resolve whether the request concerns a Project, the Job, shared workspace code,
or Moom. If the destination is unknown, ask in chat or through the harness BEFORE
creating a question file. Ask which result/entity is affected, not for a technical
diagnosis. If the owner cannot choose, create temporary docs/workspace/intake/ notes
and route them after diagnosis, preserving answers and links. A Moom defect belongs
in workspace feedback for upstream; do not silently overwrite the engine or Job.

Once scoped, questions belong under that entity's current version in docs/. Each
round gets a NEW numbered review file. Keep questions (2–3 concrete options, one
Recommended, blank Answer) separate from uncertain decisions (proposal, why
uncertain, blank Confirmation / override). Summarize new ideas, overrides and
uncertainties and link the exact artifact; full documents remain available without a
mandatory complete reread. Carry forward resolved answers.

Link the file and wait for its submission. Time, silence and blank fields before
submission are not answers. After the owner submits the round, blank fields delegate
reasonable local choices; record them as delegated, not accepted or universal rules.
Do not repeatedly ask delegated questions. Preserve submitted rounds and record
resolved decisions before opening another. Reopen only material unresolved choices.

For new iterations either create 01-request.md or adopt the owner's existing
01-*.md with --input. Never overwrite their text or other prepared documents.
If an already recorded input changes, reread it and use acknowledge-input to record
the exact new hash. Do not merely change a version number in metadata.

Human review should cost less effort than doing the work. Each Job names what the
person checks, the evidence shown, manageable review chunks and a final check across
the entire artifact. Chunking alone does not eliminate omissions or inconsistency.

Record readiness with `record STEP --artifact PATH`; acceptance additionally needs
--accepted and evidence of the person's approval of THAT revision. Passing tests,
submitted questions, comments and earlier approval are not current acceptance.
These are cooperative workflow records, not an independent authorization boundary.
