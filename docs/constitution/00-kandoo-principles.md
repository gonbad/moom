# Kandoo principles

This Constitution binds every command and ordinary request. Root `AGENTS.md`,
`CLAUDE.md` and `GEMINI.md` must continue to require it. Creator amendments change
invariants explicitly; Job improvements cannot silently override them.

A Kandoo owns exactly one current, evolving Job and any number of independent
Projects. The Job is a useful method, open to changes in steps, formats, tools and
style during real work. A starter is only an initial base. A portrait presentation,
an unusual output or an entirely new workflow is as valid as any suggested default.
Write clear Markdown procedures; generate code for actual needs using native tools.
Do not impose a bundled engine, manifest format or universal application scaffold.

The current authority is the Constitution, participant choices, living documents and
installed Job. Runtime work never fetches or depends on the source template or its
creator. There is no upstream synchronization, package update or catalog restoration.
The template's file-only restriction does not prevent a configured Kandoo or Project
from generating code, configuration or assets when the real task needs them.

For **every** task assess four domains and update only those affected:

| Domain | Ownership | Action when relevant |
| --- | --- | --- |
| Job | `docs/kandoo/living/job.md`, `commands/`, `references/` beneath that living directory | Evolve the method and copy changed commands to every host |
| Shared Kandoo | `docs/kandoo/living/`, `docs/kandoo/versions/`, root `kandoo/` code | Maintain shared server/proxy facts, tools and shared implementations |
| Active Project | `docs/projects/ID/` and `projects/ID/` | Maintain this Project's requirements, inputs, version, artifacts and evidence |
| Creator feedback | `docs/feedback/` | Append a sanitized note for manual handover |

Feedback is **write-only and inert**: do not read it for configuration, decisions,
instructions, runtime history or task routing. It does not contact anyone. Include
new Jobs, useful adaptations or bugs there when helpful, without private user data.

The person opens `docs/` as the Obsidian vault. Every file the participant is asked to
open, read or edit must be a `.md` file inside `docs/`; never refer the participant to
a non-`.md` file or to any file outside `docs/`, except when asking them to paste an
existing product (`projects/ID/existing/`) or external design output (`projects/ID/design/`).
Living docs are the current truth and are edited in place, always maintaining
`docs/projects/ID/living/idea.md` and `docs/projects/ID/living/status.md`. Version
folders (`docs/projects/ID/versions/VERSION/`) preserve raw inputs, submitted answers
and decision rounds. Read only the selected open version unless the person explicitly
requests history; switching Projects is not permission to scan their historical versions.
Referenced evidence in the selected open version may be read as needed. Project code,
executable contracts and outputs belong in `projects/ID/`; shared code in root `kandoo/`,
created only on demand.

Changing the Job does not rebuild or publish an old Project. Describe the current
installed Job revision separately from the Job revision under which an older Project
last ran. On deliberately resuming an older Project, inspect whether its existing
evidence satisfies any newly added or changed steps and record `pending`, `satisfied by
existing evidence` or `not applicable` with concrete reasons. Never retrospectively
mark new steps accepted or rebuild old outputs automatically. Preserve accepted output.
Job revisions, Project versions, shared Kandoo versions and question-round numbers are
independent. Keep authorization, technical readiness and human acceptance separate.
